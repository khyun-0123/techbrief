# 01. 고객사 요구사항

> **이 문서로 알 수 있는 것**
> * 테크브리프가 풀려는 문제와 쓰는 사람
> * 고객사가 요구한 결과물 · 환경 조건
> * 요구사항이 어떤 기능으로 이어졌는지

<sub>고객사(디스플레이 제조 기업) 기술 동향 담당자와의 인터뷰(2026-10)와 이후 회신을 **요구사항만 추려 정리**했습니다. 발언 원문 · 개인 · 사내 정보는 싣지 않습니다.</sub>

## 1. 문제

| | 내용 |
| :-- | :-- |
| 하는 일 | 사업 영역 안의 새 기술 소식이 나오면, **그날 안에** 기술 보고서 한 편을 써서 경영진(CTO · CEO까지)에게 보고 |
| 가장 오래 걸리는 단계 | 처음 보는 기술의 컨셉 · 원리를 이해하는 것 — 보고서 한 건에 **4~5시간** |
| 가장 중요한 내용 | 「우리 사업과 연결점이 있는가, 임팩트가 있는가」 (의미 · 핵심 · 연결성) |
| 쓰는 사람 | 도메인 지식이 있는 경력 담당자 (초안이 있으면 경험이 적은 담당자도 활용) |
| 바라는 흐름 | 도구가 **초안**을 주고, 담당자가 확인해 완성 |

## 2. 요구사항

| # | 요구사항 | 테크브리프에서 |
| :-: | :-- | :-- |
| R1 | **빠른 초안** — 모르는 기술도 빨리 이해할 수 있게 | 키워드 → PPT 약 2분 ([07](07_performance_ops.md)) |
| R2 | **우리 회사에 주는 의미**가 보고서의 핵심 | 특허로 계산한 「자사 위협 · 기회」 판정이 헤드라인 ([03](03_judgment.md)) |
| R3 | 보고서 구조: 컨셉 → 원리 → 장단점 → 경쟁사 동향 → 우리에게 주는 임팩트 | 자료마다 6항목 요약(컨셉 · 원리 · 장단점 · 타사 현황 · 활용 방안 · 효과성) |
| R4 | **출처 표시** — 블로그보다 논문 · 전문 출처가 더 신뢰받음 | 문장마다 근거 번호, 출처 1차 · 2차 구분 ([04](04_collection_importance.md), [05](05_ai_and_evidence.md)) |
| R5 | 기사가 많고 **중복이 매우 많음** | 같은 소식 묶기 · 중요도 100점 · 「중요」만 매일 ([04](04_collection_importance.md)) |
| R6 | **개조식 · 일관된 형식**, 받는 사람이 쉽게 이해하는 문체 | 담당자 양식 1페이지 + 유첨, 같은 틀 |
| R7 | 결과물은 **PPT** (제목 18 · 소주제 14 · 본문 11 · 주석 10pt, 사내 전용 글꼴) | 4:3 PPT · PDF · 텍스트 내보내기 |
| R8 | 그래프 같은 **시각 자료**로 가독성 | 기술 시계열 · 특허 증가 막대 · 연관 키워드 맵 |
| R9 | **쌓인 데이터로 추이 · 트렌드**를 읽고 싶음 (가장 기대하는 효과) | 기사 · 논문 12만 · 특허 127만 축적, 「요즘 뜨는 기술」 신호 점수 |
| R10 | 지난 보고서 보관함 | 「내 보고서」 (팀 공유 · 중요 표시 · 휴지통) |
| R11 | 한 화면에서 보는 방식 선호 | 대시보드에서 분석 → 자동 보고서까지 |

## 3. 환경 조건

* **망 분리:** 업무는 사내망 PC, 검색 · AI는 인터넷 PC. 인터넷 쪽에서 만들어 결과 파일만 옮기는 방식이 일반적 → 테크브리프는 **결과물을 PPT · PDF · 텍스트로** 내보내고, 사내 설치 시 수집은 인터넷 서버 · 업무망엔 파일만 ([02](02_architecture.md)).
* **파일 업로드 제약:** 사내 AI 도구에 파일을 올리기 어려움 → 파일 업로드에 기대지 않는 구조.
* **AI 모델:** 상용 · 사내 모델 모두 가능 → AI 연결을 갈아 끼울 수 있게 ([06](06_model_evaluation.md)).
* **보고 주기:** 임팩트 큰 기술은 당일 보고, 모인 정보는 월간 리포트로.
